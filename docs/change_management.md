# WenKB 变更管理说明书

版本：v0.1  
日期：2026-09-03  
阶段：变更管理  
范围：本文定义 WenKB 需求、设计、代码、数据库、配置、文档和部署运维变更的分类、评估、审批、实施、验证、发布、回滚与记录要求，为项目持续维护提供统一基线。

## 1. 文档目的

本文用于规范 WenKB 从变更提出到变更关闭的全过程，确保每项变更都可评估、可实施、可验证、可追溯和可回滚。

变更管理的核心目标是：

- 降低需求和代码变更对现有功能的影响。
- 保证需求、设计、实现、测试、部署和操作文档保持一致。
- 保证数据库、文件资源和向量数据变更可恢复。
- 为后续维护交接、版本发布和问题追责保留完整记录。

## 2. 管理范围

变更管理适用于以下内容：

- 需求范围、业务流程和验收标准。
- 总体架构、模块边界和数据流。
- 详细设计、接口约定和数据模型。
- 应用代码、前端页面和后台任务。
- 数据库结构、初始化数据和迁移脚本。
- 模型供应商、模型参数和运行配置。
- 部署方式、目录结构、备份策略和运维流程。
- 开发者手册、用户手册、测试计划和维护交接记录。

## 3. 变更分类

### 3.1 需求变更

新增、删除或调整用户角色、功能范围、业务流程、非功能要求和验收标准。

### 3.2 设计变更

调整系统分层、模块职责、数据关系、状态模型、接口结构或一致性规则。

### 3.3 实现变更

调整前端交互、后端逻辑、模型调用、文件解析、索引任务或异常处理。

### 3.4 数据变更

调整数据库表结构、字段约束、索引、初始化数据、迁移脚本或向量映射。

### 3.5 配置与部署变更

调整端口、目录、模型服务、存储位置、运行参数、部署方式或备份策略。

### 3.6 文档变更

调整需求、设计、测试、开发者手册、用户手册、部署运维或维护交接内容。

## 4. 变更等级

| 等级 | 定义 | 典型影响 | 管理要求 |
|---|---|---|---|
| C1 重大变更 | 影响核心架构、数据安全或大范围用户流程 | 数据库切换、权限体系、局域网部署 | 完整评估、专项测试、备份和回滚方案 |
| C2 重要变更 | 影响一个或多个核心业务链路 | 问答、索引、模型、接口结构调整 | 影响分析、回归测试、维护记录 |
| C3 一般变更 | 影响局部功能或文档内容 | 页面细节、提示语、普通文档修订 | 目标测试或文档校验 |
| C4 紧急修复 | 为处理阻断性故障而立即实施 | 服务无法启动、数据损坏风险 | 先恢复服务，后补齐评估和记录 |

变更等级应按潜在影响而不是修改行数判断。无法确定时，按较高等级处理。

## 5. 变更流程

### 5.1 提出变更

变更提出人应说明：

- 变更背景和问题现象。
- 变更目标和预期结果。
- 涉及的业务范围。
- 期望完成时间。
- 是否存在紧急性或外部依赖。

### 5.2 影响分析

实施前应至少分析：

- 对需求和用户流程的影响。
- 对架构、接口和数据模型的影响。
- 对数据库迁移和历史数据的影响。
- 对文件资源、向量索引和模型配置的影响。
- 对安全性、性能、可靠性和兼容性的影响。
- 对测试范围、部署步骤和回滚方案的影响。

### 5.3 评审与批准

- C1 变更必须经过需求、设计、测试和部署影响评审。
- C2 变更至少需要开发和测试确认。
- C3 变更由实施人员完成自检并更新相关文档。
- C4 变更可先执行恢复动作，但必须在事后补充记录和复盘。

### 5.4 实施变更

实施时应遵循：

1. 先确认工作区状态和当前版本。
2. 先备份受影响的数据和配置。
3. 按批准的方案修改代码、数据或文档。
4. 保持改动范围可控，避免夹带无关重构。
5. 为变更补充或更新测试。
6. 更新受影响的文档和维护交接记录。
7. 创建可追踪的 Git commit。

### 5.5 验证变更

验证内容至少包括：

- 变更目标是否实现。
- 受影响功能是否通过。
- 核心回归链路是否通过。
- 数据库、文件和向量数据是否一致。
- 升级、重启和异常恢复是否正常。
- 相关文档和导航是否同步。

### 5.6 发布与关闭

验证通过后，应记录发布版本、发布时间、验证结果和遗留风险。满足关闭条件后，变更状态才可改为“已关闭”。

## 6. 代码与文档同步规则

### 6.1 需求变更

需求变更至少同步检查：

- 需求分析说明书。
- 概要设计说明书。
- 测试计划。
- 用户手册或开发者手册。

### 6.2 设计变更

设计变更至少同步检查：

- 概要设计。
- 详细设计。
- 数据库设计或接口设计。
- 相关测试项。

### 6.3 代码变更

代码变更至少同步检查：

- 详细设计中的实现约束。
- 测试计划和回归测试。
- 开发者手册。
- 部署运维和维护交接记录。

### 6.4 文档变更

文档变更应同步更新：

- `AGENTS.md` 中的文档导航或待办状态。
- 相关文档测试。
- 代码维护交接记录。

## 7. 数据库与索引变更

- 每次结构变更必须新增可识别的迁移版本。
- 迁移前必须备份数据库、上传文件、文档资源和向量库。
- 迁移脚本应支持重复执行保护或明确的失败处理。
- 迁移后必须检查数据库版本、核心表、索引状态和关键业务流程。
- embedding 模型变化可能导致历史向量失效，必须评估重建范围。
- 数据库和向量库无法同时回滚时，应以关系型数据库为业务基准，并重新构建向量索引。

## 8. 测试与质量门禁

变更交付前应根据等级执行测试：

| 变更等级 | 最低验证要求 |
|---|---|
| C1 | 全量自动化测试、专项测试、升级恢复验证和核心流程验收 |
| C2 | 受影响模块测试、核心回归测试和必要的数据一致性验证 |
| C3 | 目标测试、文档测试或静态检查 |
| C4 | 故障恢复验证，事后补充完整回归和复盘 |

以下情况不得直接关闭变更：

- 核心测试失败。
- 高优先级缺陷未处理且无批准结论。
- 数据迁移没有备份或回滚方案。
- 设计、实现和测试文档存在明显矛盾。
- 变更结果无法稳定复现。

## 9. 版本与提交管理

- 每项独立变更应使用独立的 Git commit。
- commit 信息应能够概括变更目的。
- 变更记录应关联 commit、版本或其他可定位标识。
- 不应使用整体回退覆盖用户已有的无关修改。
- 发布版本应能够定位到对应源代码和文档状态。

## 10. 回滚与应急处理

### 10.1 回滚触发条件

- 服务无法正常启动。
- 核心流程出现阻断性故障。
- 数据库迁移失败或数据结构不完整。
- 关键数据、文件或向量索引出现不可接受的不一致。
- 安全问题需要立即撤销变更。

### 10.2 回滚顺序

1. 停止继续扩大影响的任务或服务。
2. 保留日志、错误信息和当前现场。
3. 恢复代码或配置版本。
4. 按备份恢复数据库和资源目录。
5. 检查向量库与关系数据一致性。
6. 启动服务并执行健康检查。
7. 执行核心流程冒烟和回归测试。
8. 记录回滚结果与后续修复计划。

## 11. 变更记录模板

每项变更建议至少记录以下字段：

| 字段 | 内容 |
|---|---|
| 变更编号 | 唯一编号 |
| 变更标题 | 简短描述 |
| 提出人 | 变更发起人 |
| 实施人 | 实际执行人 |
| 变更等级 | C1 / C2 / C3 / C4 |
| 变更类型 | 需求、设计、实现、数据、部署、文档 |
| 变更原因 | 背景和问题 |
| 影响范围 | 模块、数据和用户流程 |
| 实施方案 | 操作步骤和注意事项 |
| 测试结果 | 测试项、结果和缺陷 |
| 回滚方案 | 触发条件和恢复步骤 |
| 关联版本 | 版本号或 Git commit |
| 文档同步 | 已更新的文档 |
| 关闭结论 | 通过、延期或回滚 |

## 12. 当前项目执行要求

结合 WenKB 当前维护规则，后续每次变更至少应做到：

- 先阅读需求、设计、测试和维护交接文档。
- 先确认工作区状态，不覆盖无关修改。
- 变更后补充或更新相关测试。
- 文档变更同步更新 `AGENTS.md` 和维护交接记录。
- 交付前执行必要验证并创建 Git commit。

## 13. 验收标准

变更管理文档应满足：

- 能覆盖需求、设计、代码、数据、部署和文档变更。
- 能明确变更等级、评审流程、测试要求和回滚条件。
- 能保证项目文档、代码、测试和部署状态可追溯。
- 能作为后续维护交接、版本发布和问题复盘的依据。
